  <name>Task 1: Fix GGUF parser bounds checking to prevent OOM</name>
  <files>app/src/main/java/com/warped/data/local/inference/GgufMetadataParser.kt</files>
  <action>
Add bounds validation before every `ByteArray(stringLength)` allocation in the GGUF parser. A valid GGUF metadata key/value string is at most a few hundred bytes. If the length read from the file exceeds 4096 bytes (or is negative), the file is corrupted — break out of the parsing loop.

**Add constant:**
```kotlin
private const val MAX_STRING_LENGTH = 4096
```

**Guard the `keyLen` allocation (line 50-53):**
```kotlin
val keyLen = ByteBuffer.wrap(keyLenBuf).order(ByteOrder.LITTLE_ENDIAN).long.toInt()
if (keyLen < 0 || keyLen > MAX_STRING_LENGTH) break
val keyBytes = ByteArray(keyLen)
```

**Guard each `strLen` allocation in the `when` branches (lines 63-67, 71-75):**
For the `general.name` block:
```kotlin
val strLen = ByteBuffer.wrap(strLenBuf).order(ByteOrder.LITTLE_ENDIAN).long.toInt()
if (strLen < 0 || strLen > MAX_STRING_LENGTH) break
val strBytes = ByteArray(strLen)
```

For the `general.architecture` block:
```kotlin
val strLen = ByteBuffer.wrap(strLenBuf).order(ByteOrder.LITTLE_ENDIAN).long.toInt()
if (strLen < 0 || strLen > MAX_STRING_LENGTH) break
val strBytes = ByteArray(strLen)
```

Also fix `skipValue` (line 137-146) — the `type == 8` case reads a length and skips bytes. Guard with the same max:
```kotlin
val len = ByteBuffer.wrap(lenBuf).order(ByteOrder.LITTLE_ENDIAN).long
if (len < 0 || len > MAX_STRING_LENGTH) { raf.skipBytes(0); return@skipValue }
raf.skipBytes(len.toInt())
```

Note: For `skipValue`, the method signature doesn't return a value, so use `return` (labeled return from the lambda/function scope — use `return@skipValue` won't work since skipValue is a regular function). Just do an early return without the label since `skipValue` returns Unit.
</action>

Fix misleading error handling: the `catch (e: OutOfMemoryError)` block in `downloadFile()` (lines 138-145) is redundant since `ModelDownloadManager` already catches OOM internally and wraps it in `Result.failure`. The separate `catch (e: OutOfMemoryError)` would only trigger if OOM happens OUTSIDE of `downloadModel()` (e.g., in UI state updates). Remove the duplicate `catch (e: OutOfMemoryError)` block entirely — the `catch (e: Exception)` block + the `onFailure` handler already cover all error cases. If a genuine non-recoverable OOM occurs, the JVM will terminate the process, which is more honest than showing a fake "Not enough memory" message.
