## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `colorScheme.surface` / `background` (theme-resolved) | Chat background, surfaces |
| Secondary (30%) | `colorScheme.surfaceContainer` (input pill, cards) | Chat input pill, message bubbles, attachment chip background |
| Accent (10%) | `colorScheme.primary` | Send affordance, draft play/pause icon tint, LinearProgressIndicator fill |
| Destructive | `colorScheme.error` | Draft delete affordance (no new destructive actions in this phase) |

Accent reserved for: send affordance, draft play/pause icon tint, draft + bubble LinearProgressIndicator fill. The attach button uses the default content tint (same as the image-attach sibling — attachment is a neutral affordance, not a CTA). The chip remove-X uses `onSurfaceVariant` (neutral — removal is non-destructive, per-turn only). Never accent for error/notice text; never error-red for the remove-X or the unavailable/unsupported notices. Source: Phases 67–69 contracts, extended with attach-neutral rule.

Attachment-chip color rule: chip background `colorScheme.surfaceContainer` (same as input pill / text bubbles / draft card); leading doc icon tint `onSurfaceVariant`; filename `onSurface`; size + truncation marker `onSurfaceVariant`. No accent fill, no pulsing, no recolor when attached — the chip's presence is the only attached-state signal.

Document source card color rule: the turn's document source renders inside the existing Fuentes surface with the exact same card chrome (container color, corner shape, padding) as web-source cards — filename where a web card shows its title/host. Same `onSurfaceVariant` metadata styling. No new colors.

## Screens / Surfaces (Phase 70 scope)

Exactly three surfaces change, all in the chat flow. No new screens, no new dialogs, no drawer/settings changes. TOOL-03 (unit converter) is contingency-only per CONTEXT.md — no UI surface unless the planner triggers it with evidence.

- Visual anchor (focal point): the conversation turn list remains the primary anchor — the attachment chip, truncation notice, and document source card are subordinate elements that never compete with message content for attention.

### Surface 1 — Attach affordance in `ChatInputBar`

- Paperclip-style `IconButton` (`Icons.Filled.AttachFile`) in the same icon row as the image (`AddPhotoAlternate`), dictation (mic), and voice-send (waveform) affordances. Exact order within the row at executor's discretion, but it must sit in that row — never in the text field, never in a menu.
- Size 40dp, matching the image-attach sibling. Disabled (not hidden) whenever `inputLocked` is true, mirroring `onAddImage` gating.
- Opens the system picker (SAF, `ActivityResultContracts.OpenDocument` with `text/plain`-family MIME filter) — no storage permission prompt, per-file user grant, read-only (locked by CONTEXT.md).
- Content description: "Attach document". When a document is attached, description becomes "Replace attached document" (new pick replaces — one document per turn, locked by CONTEXT.md).
- TalkBack: state announced via `stateDescription` (Phase 65 pattern) — "Document attached: {filename}" style when attached.
- Same UX local + remote: the affordance never changes by endpoint type (provider differences stay behind the capability matrix, locked by CONTEXT.md). No model gating on the attach button — grounding works on both paths.

### Surface 2 — Attachment chip above `ChatInputBar`

- Persistent chip row directly above the chat input (same slot as the image-preview row and the Phase 67/68 recording/draft rows). Visible whenever VM attachment state holds a picked document.
- Chip contents left-to-right: doc icon (`Icons.Filled.Description` at executor's discretion within Filled set) + filename (Label 14sp, single-line ellipsis) + size readout (`· 12 KB`, Label 14sp `onSurfaceVariant`) + remove X (≥48dp hit target, `onSurfaceVariant` tint).
- Size format (prescriptive): under 1 MB render whole KB (`842 KB`); at/above 1 MB render one-decimal MB (`2.4 MB`). Bytes computed from the pre-read size check (locked by CONTEXT.md).
- Truncation marker: when content exceeds the cap, the chip appends the truncation notice inline — size readout becomes `· 12 KB · showing first N chars` (N interpolated, Label 14sp `onSurfaceVariant`). Never silent, never blocked (locked by CONTEXT.md). The full notice also goes through the Snackbar channel on send (Surface 3 copy contract).
- Remove X discards the attachment immediately — no confirmation dialog (non-destructive: per-turn only, nothing persisted, mirrors image-remove single-tap and Phase 67/68 cancel/delete precedent).
- Caption text stays editable alongside the chip; send transmits text + document as one turn. The chip must not cover or disable the text input.
- Rotation keeps the attachment (VM-owned state + already-read bounded content in memory — per-turn, never Room, locked by CONTEXT.md). Backgrounding keeps the chip; no foreground service.

### Surface 3 — Document source chip in the turn + notice channel

- The grounded turn renders the document in the existing Fuentes surface: same card chrome as web-source cards, filename as the card label, truncation marker (`truncated at N chars`) as card metadata where a web card shows host/status. Tapping the card opens `SourcePreviewSheet` with the bounded content start. Zero document cards render when grounding was skipped (model-only fallback) — the turn shows only the notice.
- All user-visible notices go through the existing `SnackbarHost` channel (`SnackbarDuration.Short`): truncation notice on send, unsupported-format message on pick, failed/empty-read notice on send. Assistant bubble copy itself is model-generated and unconstrained — only the notice/Snackbar copy is contracted below.
- Send is never dead-ended: unsupported pick keeps the text sendable (chip never appears for binary); failed/empty read sends text-only with the fallback notice (locked by CONTEXT.md).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Attach document (attach button content description; "Replace attached document" when a document is already attached) |
| Chip remove | Remove attached document (remove-X content description — single tap, no confirmation) |
| Truncation notice | Showing first N chars of {filename} (chip inline marker + send Snackbar, `SnackbarDuration.Short`) |
| Unsupported format | Can't read {filename} yet — text files (.txt, .md) only (pick-time Snackbar, `SnackbarDuration.Short`; chip never appears, text stays sendable) |
| Failed/empty read | Couldn't read {filename} — answering without it (send-time Snackbar, `SnackbarDuration.Short`; text-only answer proceeds) |
| Source card | {filename} + truncated at N chars metadata when truncated (Fuentes card label/metadata) |
| Empty state heading | n/a — no attachment renders no chip (normal input row, not an empty state) |
| Empty state body | n/a |
| Error state | The three Snackbar rows above (truncation / unsupported / failed-read — each states the problem + what happens next) |
| Destructive confirmation | none — removing the attachment is non-destructive (per-turn only, nothing persisted): single tap, no dialog |

Bilingual note: Help/empty-state copy in this app ships EN+ES (Phase 64 precedent). All five new user-visible strings (attach/replace descriptions, remove description, truncation, unsupported, failed-read) must be added to `strings.xml` with ES translations following the existing `values-es` pattern. New keys use the `doc_reader_*` prefix (sibling to Phase 67 `voice_msg_*` keys).
